# Stash — implementation tracker

Sources of truth, in order: `Stash — Kotlin Multiplatform Architecture Plan.md` (architecture),
`Stash — Design Handoff Spec.md` (UI; wins over the prototype), `Stash — App Screens & Prototype – 09 Interactive prototype.html` (behaviour).
Backup and restore are out of scope for this iteration.

Minor findings are parked in `docs/BACKLOG.md` (operator decision, 13 Nov); only Critical and Major findings get a fix and re-verification here.

Status words: Pending / In Progress / Review / Blocked / Complete. Android and iOS: Verified / Failed / Not Verified.

## Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | No backup code: no `backup/` modules, `BackupPolicy`, `operation.backed_up_at`, `GoogleAuth`, `SecureStore`, Drive REST or "backup due" fan-out. The existing disabled "Account and backup (Phase 2)" settings group stays as it is. | Operator scope; operator said to leave the group untouched. |
| D2 | `saved_item.updated_by_device`, `saved_item.version` and `operation.device_id` are left out. | They exist only for restore merge; an additive migration adds them with backup. |
| D3 | `core:domain` may depend on `androidx.paging:paging-common` in addition to stdlib, coroutines and kotlinx-datetime. | The plan's `ItemRepository` returns `PagingData`, which contradicts its own dependency rule 1. |
| D4 | `ShelfQuery` is the pure reference for filter, sort, group and search. The database implements the same filter and sort in SQL; group headers are inserted between paged rows with the domain's label function; chip counts come from SQL aggregates. A parity test compares both. | A pure policy over the full item list cannot serve 50,000 items without loading them. |
| D5 | Source chips: only sources with at least 2 items, at most 12, ordered by count then newest. Page size 30. | Handoff spec. |
| D6 | Swipe settings are stored as start/end, not left/right. | Handoff spec (RTL). |
| D7 | Compact, medium and expanded width classes are all in scope. | Operator. |
| D8 | Fonts stay bundled through Compose resources. | Architecture plan; already shipped this way. |
| D9 | The in-app reader screen embeds a platform web view (Android `WebView`, iOS `WKWebView`) under the shared `ReaderTopBar`; "Open links in: Browser" uses `BrowserLauncher` (Custom Tabs / `SFSafariViewController`). | The prototype's reader has its own top bar with Aa and Mark unread, which a Custom Tab cannot host. |
| D10 | Paper texture tile, pull-to-refresh quill animation and new es/hi/ta translations are not supplied. Texture and quill are left out (standard pull-to-refresh indicator); new strings fall back to English. | No assets; do not invent them. |
| D11 | Search matches when every query token is a prefix of a word in the title or site name, case-folded. Tokens and words are split by the same rule (D16), not by whitespace. The database uses FTS4 over `title` and `site_name` only, queried as `MATCH '"tok1*" "tok2*"'` (star inside the quotes); a query with no tokens issues no `MATCH`. | Plan and handoff both specify FTS; substring search (prototype) cannot use an index at 50,000 items. Description and URL are not shown on results, and the policy table says "title + site". |
| D12 | Settings changes go through `CommandBus` as `ChangeSetting(transform)` but write no `operation` row; `SettingsRepository` is read-only in the domain. | The plan logs settings changes only so backups capture them. A transform applied atomically avoids lost updates from snapshot writes. |
| D13 | A day with no read is safe for the streak when nothing was unread at the end of that day. The data layer keeps `unreadZeroSince` and the pure `StreakEngine` derives rest days from it. | Handoff rule 2; the streak "ends at midnight", so midnight is when the shelf is judged. Recording only what the app happens to see breaks on days the app is not opened. |
| D14 | Database and settings files live in Application Support on iOS, not Documents. | Documents is user-visible in Files; moving later needs a migration. |
| D15 | A reminder plan holds today's remaining slots plus tomorrow's daily reminder and, after a read, tomorrow's streak-saver slots. That is at most 5 pending (before 9 AM with nothing read: today's four plus tomorrow's daily); the architecture plan says 4. | Otherwise the saver, and the daily reminder, never fire on a day the app is not opened. iOS allows 64 pending. |
| D16 | Search words are runs of letters, digits and the combining marks of Devanagari and Tamil. `SearchMatcher` and the FTS4 `unicode61` tokenizer (`remove_diacritics=0`, `tokenchars=` the same marks) use the same set, exposed as one constant in the domain. | Without the marks both tokenizers split Hindi and Tamil words at vowel signs, so `हिंदी` searches for `ह` and `द`. Hindi and Tamil are app languages. |
| D17 | Metadata and reader fetches upgrade `http://` to `https://`, on the first request and on every redirect hop. The saved URL is not changed. | Android (target SDK 37) and iOS block cleartext by default, so `http://` fetches would fail and be reported as offline. Whether the reader's web view may load cleartext pages is decided with the platform work. |
| D18 | `PageMetadata` carries the final URL after redirects and no site name. The data layer derives domain, site name, source key and content type from the final URL with `LinkCapturePolicy`; the site name stays the registrable domain. | Handoff: "Site name: registrable domain". A link saved through a shortener should show the real site. |
| D19 | `core:platform` defines only the capability interfaces that have a consumer. For the data layer: `ShareInbox`, `NotificationScheduler`, `WidgetPublisher`, `BackgroundJobs`. UI-facing capabilities are added with the UI and platform tasks. | No interface without a caller. |
| D20 | `core:platform` gains `Connectivity` (is the device online). A metadata fetch that fails as offline counts toward the three attempts only when the device reports it is online. | Counting every offline failure fails links saved on a plane; counting none leaves a dead domain pending forever (DNS and TLS errors are reported as offline). |
| D21 | Reading is a command: `MarkRead` and a new `OpenItem` record the streak day in the same transaction as the item change, and the result carries the celebration. `StreakRepository.recordRead` is removed. | The plan lists "record the streak" as command fan-out. With a separate call the UI had to remember it, and a read from any other path did not count. |
| D22 | `ShareInbox.drain(save)` hands entries over one at a time and removes each only after `save` returns; when `save` throws the drain stops and keeps that entry and the later ones. | The first contract returned a list, so a link was lost if the app died or the save failed after the drain. |
| D23 | `MetadataFetcher` parses only the document head; reading time comes from JSON-LD or a linear scan of the body text that builds no DOM. The reader keeps a best-effort size guard. | A crafted 396 KB page built a 234 MB document on every save, and each pre-scan guard was beaten by a new variant. Metadata lives in the head, so the save path can be immune by construction. |
| D24 | Android components that need the data layer or capability types (WorkManager workers, the Glance widget, `ShareReceiverActivity`, the time-change receiver) live in `shared/androidMain`; those that need neither (alarm scheduler, posting receiver, boot re-arm, activity registry) live in `core:platform/androidMain`. `androidApp` holds only the application class, `MainActivity`, the manifest and launcher resources. | The plan lists these under `androidApp`, but rule 5 limits `androidApp` to `shared`'s public API, which does not expose the core modules. |
| D25 | Contract changes from the T3.0 review: no `Haptics` capability (composables use Compose's `LocalHapticFeedback`); new `WidgetPinner`; `NotificationPermission.openSettings()`; `AppLocale.current` (the OS owns the app language, so the language row reads it rather than a stored preference); `Clipboard.peekLink()` never prompts and `readUrl()` runs only on the user's "Use"; `DeepLinks.consumed(itemId)` keeps a newer link. | Each would otherwise have forced a contract change after Android, iOS and the UI were built: no View for haptics on Android, no way to pin a widget, no recovery from a denied permission, a stale language selection, an iOS paste prompt on every Add-link open, a dropped second deep link. |
| D26 | The iOS share inbox is a directory in the App Group container with one JSON file per shared payload, written under a temporary name and renamed into place; the app reads, saves and then deletes each file. No file coordination or locks. | The plan's single appended `inbox.jsonl` needs cross-process coordination, which fails in the simulator test runner and risks a lock held by a suspended extension. Atomic rename gives the same guarantees (no partial reads, no lost appends, re-delivery after a crash) with plain file operations. |
| D27 | Reminders stay on by default, and the app asks for notification permission ONCE, the first time the shelf holds an unread item while the app is in the foreground (in practice right after the first save). A denial is respected: no automatic re-ask; the reminder switches in Settings show that notifications are off and offer the system settings. | On a fresh install reminders were planned but the permission was never requested unless the user toggled a switch off and on, so reminders silently never appeared (found on the physical phone). Asking at launch with an empty shelf has no context. |
| D28 | Cards, the item sheet header and search results show the item's image when it has one (Coil, https only), with the monogram tile as placeholder and fallback. | The plan and the handoff both specify thumbnails; 25 of 38 saved items on the test phone had an image and none was shown. |
| D29 | "Phone landscape" is a window whose HEIGHT is under 480 dp. Such a window is never list-detail, whatever its width: it uses the single-pane layout with the medium-width rules (list 640 dp centred, sheets 560 dp, reader column 680 dp), the header collapses on scroll, the nudge banner hides and the streak chip carries the urgency colour. List-detail needs width ≥ 840 dp AND height ≥ 480 dp. | The operator's phone (423 × 941 dp) showed the tablet two-pane layout when turned sideways, because only width was tested. The handoff has a separate "Phone landscape" row. 480 dp is Material's compact-height limit. |
| D30 | Device checks run once per form factor (Android phone, Android tablet, iPhone, iPad), not repeated on an emulator and a physical device of the same form factor. The physical phone is used only for what an emulator cannot show: real performance numbers, the manufacturer's share sheet, system backup, final sign-off. Idle emulators are shut down. | Operator decision, 14 Nov: repeating the same check on two phones doubled the time and tied up the operator's personal phone. |
| D31 | `:androidApp`'s `benchmark` build type (release + R8, debug-signed, not debuggable) may depend on `:core:database` for a measurement-only seeder that inserts and wipes synthetic items; `checkModuleGraph` allows this for the `benchmark*` configurations only. The seeder is absent from `release` and `debug`. | 50,000 back-dated items cannot be created through the command bus (it stamps "now" and re-plans per item); writing raw SQL beside Room risks locking and skips invalidation. |

## Open questions for the operator

- Dark theme with the Oxblood accent gives 4.31:1 for the reader toolbar's site line (`on-primary-muted` on `primary`), below the 4.5:1 the handoff promises. The handoff values are kept; a designer needs to pick a new value.
- The app icons on both platforms are provisional art generated from the prototype's icon tile (Playfair "S"); the handoff lists the final wordmark as open.

- Android `android:allowBackup`: DECIDED 14 Nov (operator): switched to `false`, so Android no longer backs Stash's database and settings up to the cloud. On Android 12+ some manufacturers still copy app data in a cable / device-to-device transfer; excluding that needs `dataExtractionRules` (not done). iOS: app data is still part of the device's iCloud / computer backup (not changed, not asked).

Evidence, 14 Nov, physical phone: with `allowBackup="true"` the phone's Google backup held Stash's database and settings, and a reinstall restored them together with a home-screen widget. Verified on the same phone at `7c59efe` (uninstall, install): no Stash data restored (empty shelf, default settings, no data directories before first launch), no widget; the package no longer carries `ALLOW_BACKUP`. Android still logs a restore-at-install check for the package (it restores only the system's package list).

## Build and test commands

- Module graph: `./gradlew checkModuleGraph`. Domain coverage: `./gradlew :core:domain:koverVerify` (≥ 80% lines).
- Whole build: `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer ./gradlew check --continue` (1,537 tests at commit `93e8ad2`, 0 failures).
- Pure modules: `:m:jvmTest`, `:m:iosSimulatorArm64Test`. Android library modules: `:m:testAndroidHostTest`, `:m:iosSimulatorArm64Test`. `core:database`: `jvmTest`, `iosSimulatorArm64Test`.
- Apps: `./gradlew :androidApp:assembleDebug`; iOS `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project iosApp/iosApp.xcodeproj -scheme iosApp -configuration Debug -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' -derivedDataPath build/ios ARCHS=arm64 build`.
- New module: `include(":x:y")` in `settings.gradle.kts` plus a `build.gradle.kts` applying `stash.kmp.pure`, `stash.kmp.library`, `stash.kmp.compose` or `stash.kmp.feature`.
